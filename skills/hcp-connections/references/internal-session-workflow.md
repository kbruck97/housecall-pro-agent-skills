# Authorized Alpha/internal-session workflow

## Choose transport before clicking

Use the supported public API when sufficient for the authorized task. For UI-backed tasks the public API cannot satisfy, prefer a verified authorized Alpha/internal-session API over UI clicking. This is an operational preference, not a claim that all web features expose usable APIs. Browser control is for secure login/MFA/session bootstrap when necessary, visual verification, and authorized operations with unavailable API routes. Never use another surface to bypass access denial.

The optional `hcp-connections` skill now supplies a bounded local `local_sessions.py` helper for interactive login, encrypted per-company session persistence and fixed identity GET verification. It is not a general HCP API client or a tested Windows deployment. This reference remains the policy for other adapters. Historical observations are discovery leads, not present support or permission. Agents with only browser tools must explain the missing secure HTTP/session capability; do not pretend it exists, dump cookies through browser evaluation, or improvise a secret-bearing shell command. An approved UI/manual path may remain available, but is not an API execution claim.

## Local connection lifecycle

Load `hcp-connections` when a local internal session must be created, checked, reused or removed. Use its bundled helper instead of inventing a cookie extraction flow. Public API keys held in 1Password remain a separate connection: they do not mint HCP website sessions, and session cookies need not be put in the shared environment.

1. **Resolve the requested company.** Obtain its exact UUID from trusted company configuration or a verified mapping between public `/company` identity and internal `organization_uuid`, using that company's existing API key where available. When only a name is known, resolve it before connecting; do not assign the identity of whichever account happens to log in to the requested name. Do not send a public API key to the internal web origin.
2. **Try the saved session first.** Run `status --company-id <expected-uuid>` with the local helper. It loads only that company's encrypted session, calls the fixed `/alpha/pro` identity GET with redirects disabled, and compares `organization_uuid` exactly. A file or cookie's existence alone is not a connection. Recheck identity before each operation/adapter reuse; do not cache a positive company check across account changes.
3. **Prompt only when login is needed.** Missing session, explicit expiry, or a verified unauthenticated response leads to a single interactive `connect`. Tell the user: “Sign in to Housecall Pro for [company] in the window I opened and complete any verification there. I will verify the company and save this connection on this computer.” Never ask them to send a password, cookie or MFA code in chat. A network error, 403, wrong company, changed response schema, locked vault or unavailable browser runtime is a different blocker; do not replace saved state or repeatedly prompt for login.
4. **Acquire the cookie through normal sign-in.** The helper opens a dedicated, nonpersistent Playwright browser context at HCP's official HTTPS site. The user completes login and MFA there; after a browser reports signed in, company identity still must be verified. The runtime reads only HCP-scoped session and CSRF cookies in memory and passes them to a pinned, separate HTTP client that verifies identity. No personal browser cookie database decryption, developer-tools cookie copying, raw state export, screenshot of credentials, or secret-bearing command is required. The dedicated window may not have the user's usual 1Password extension; autofill availability must not be promised.
5. **Save only after company verification.** The helper encrypts the cookie bundle with an independent key held in the current user's native OS vault, binds the ciphertext to the expected UUID, and atomically replaces that company's encrypted file. A failed/cancelled/wrong-company login must preserve the old saved session and every other tenant. The login password and MFA code are never stored by the helper. The current helper reuses a saved session for at most 30 days after login, or until earlier expiry/revocation; this is a local reuse-age cap, not an HCP expiry guarantee. Expired encrypted material remains until a successful reconnect replaces it or an explicit forget removes it.
6. **Reuse across requests.** Five companies produce five separate session records. Returning to company B after E loads B's record and validates B again; it does not reuse E's last browser tab. Save refreshed cookies only after successful identity verification. CSRF presence and identity success do not prove that an arbitrary write is supported or authorized. Other actions still need a separately reviewed adapter and exact-operation readback.
7. **Reconnect or forget.** On missing/expired login, run `connect` again and let the user sign in. Do not repeatedly try credentials or bypass denied access. `forget --company-id <uuid>` is an explicit local removal request: remove only that company's saved ciphertext, metadata and vault key; a harmless lock file may remain to serialize operations. It is not HCP server-side logout or revocation, and it does not affect another computer.

### Local storage and portability

- Windows: `%LOCALAPPDATA%\TSM\HousecallPro\<company-uuid>\session.enc` and `metadata.json`. A per-company encryption key resides in Windows Credential Manager with **local machine** persistence, associated with the signed-in Windows user.
- macOS: `~/Library/Application Support/TSM/HousecallPro/<company-uuid>/session.enc` and `metadata.json`, with the per-company key in that user's macOS Keychain.
- The secret store uses service `TSM.HousecallPro.local-session.v1.<company-uuid>` and account `<company-uuid>`. Files contain encrypted session data or nonsecret connection metadata, never raw cookie values. Restrictive file permissions are applied where supported; OS-vault access remains subject to the operating system.
- Store outside repositories, shared/synced project folders and shared 1Password developer environments. Each user/computer establishes its own sessions. Encryption is not a promise against a compromised or fully unlocked local account.
- The shipped helper is optional and requires Playwright, its Chromium runtime, keyring and cryptography. Native vault availability must be checked; plaintext/fallback keyring backends are refused. The runtime adapter must be permitted by the calling agent's tool policy; these instructions do not authorize an alternate browser controller where that is prohibited.

### Five-tenant example

Connect fictional companies A through E by their trusted UUIDs. After each verified login, only that company's encrypted record is replaced. A later “read B's event” request verifies B's saved session, then uses a separately reviewed event-read adapter. If B's session has expired, only B prompts for a new login; A, C, D and E remain saved. Never claim this example was tested on five real tenants merely because synthetic isolation tests pass.

## Practical sequence

1. **Scope and capability.** Resolve tenant/company, exact targets, operation, read/write mode and approval from trusted configuration. Inspect actual available tools. Require a secure session provider and an HTTP request facility that enforces the controls below. Read-only collection stays GET-only. Public access failure requires diagnosis, not automatic private fallback; private-surface opt-in is separate from exact-operation authorization.
2. **Authorize login.** Bind the intended account and tenant before opening the legitimate HCP login origin. Use the runtime's vault/secure login and MFA facilities or human completion; never request passwords, cookies or OTPs in chat. Reuse a valid same-tenant session rather than repeatedly initiating login. MFA and permission checks are not obstacles to bypass.
3. **Protect the session.** The authorized login yields a protected session cookie/context. Historical HCP web observations used `_housecall-web_session_with_domain` on `pro.housecallpro.com`; neither that name nor a cookie alone proves current authentication requirements. Keep cookies, CSRF tokens and any storage state inside per-tenant isolated session jars/secret storage. Use restrictive owner-only storage (directory 0700, files 0600 or equivalent), expiry/retention controls, and a scoped opaque handle where tools support it. Never share jars between tenants or export secrets into chat, logs, skill files, archives, command arguments, screenshots or network traces. Do not export raw HAR/storage-state files. If the runtime cannot transfer a session securely to its HTTP facility, stop at that capability gap.
4. **Verify the current request contract.** From approved adapter documentation or narrowly scoped, authorized inspection of the current web client's requests, establish the exact allowed HTTPS host, method, path, parameter/body schema, response envelope, CSRF/header requirements and readback operation. Inspect only what is needed; keep secret-bearing values in the secure runtime and retain sanitized schema facts only. Historical `pro.housecallpro.com/alpha/...` templates are not a wildcard allowlist. Do not guess an identity endpoint or discover writes by submitting probe mutations. Do not claim that cookies alone suffice or that CSRF is never required. If required headers or schemas cannot be established securely, block the operation.
5. **Prove identity before work.** Through a currently verified read capability, read back the authenticated account/company and compare with the trusted expected tenant, then read the exact target and validate customer/property relationships before collecting children or writing. A loaded dashboard, HTTP 200, or taxonomy list alone is not identity proof. Recheck after login, refresh, account switching or any uncertain binding; switching tenants uses a different isolated jar. Missing identity capability or a mismatch blocks work.
6. **Issue scoped API requests.** Use the verified internal HTTP/session context instead of repeated DOM navigation/clicking. Enforce the allowed host/method/path, validated parameters and bounded pagination/time budgets before every request; reject arbitrary model-supplied URLs. Disable automatic redirects for authenticated requests and revalidate each redirect before any follow-up; never forward HCP credentials cross-origin. Keep public-key, OAuth, internal-session and third-party attachment clients separate. Third-party signed downloads use a fresh unauthenticated client under a validated destination policy. Check content type/envelope and row scope: HTML login responses, ignored filters, malformed JSON and incomplete pages are failures/partial evidence, not empty success.
7. **Guard any write.** Read current before-state, show the exact target/fields/relationships and notification or financial side effects, obtain exact-operation authorization, and persist a sanitized intent. Submit once through the allowlisted operation; save the safe receipt and read back the exact operation's target, expected fields and relationships. Report submitted versus verified distinctly. An ambiguous timeout or post-acceptance local error requires reconciliation, not retry; neither session refresh nor UI fallback authorizes resubmitting an ambiguous write. A domain skill's stronger approval/consent/idempotency rules still apply.
8. **Expire and recover safely.** Treat 401 or a login redirect as possible expiry or wrong binding, not automatically expiry. Pause, diagnose, and if authorized re-authenticate once via the secure flow; verify identity again before one bounded GET retry. Stop on repeated failure. For 403/access denial, stop and seek administrator resolution; do not switch accounts, origins or UI to evade denial. On schema drift or unavailable routes, report the limitation and use only an independently authorized UI/manual path if available. Never infer that a write failed merely because its response was lost. Invalidate expired state and remove it under the runtime's retention policy.
9. **Report without secrets.** Log operation alias, surface, timestamp, sanitized status/error class, scope-check booleans, coverage and readback outcome, not raw request/response bodies, headers, cookies, tokens, signed URLs or customer content. Keep private runtime object references out of public artifacts. State the chosen surface and unresolved prerequisites. This pack's synthetic helper checks do not verify live HCP login, native Windows/Mac vault behavior, or endpoint availability.

## Synthetic decision checks

- Public task fully covered: use public API, no browser bootstrap needed.
- Public lacks property detail; approved internal route and secure session/HTTP tools exist: bootstrap only if needed, verify identity, then internal API rather than UI clicking.
- Only browser tools exist: explain secure HTTP/session gap; approved UI/manual work is a separate fallback.
- Stale cookie or login HTML: pause/re-authenticate within budget and recheck identity; not empty data.
- Wrong tenant or unavailable identity readback: block before target work.
- Unknown CSRF/body schema or unallowlisted method/path: block; no guessed request.
- Access denied: stop; alternate transport must not evade permissions.
- Write times out after submission: reconcile exact target, no automatic retry or duplicate UI action.
- Signed attachment redirects off origin: no HCP credentials on the download client.
